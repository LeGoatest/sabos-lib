# Web Presentation and Delivery Models

**Axis:** rendering location, route/navigation ownership, document delivery, client behavior and content freshness. Several entries describe independent properties.

| Model | Definition / responsibility | Good fit | Principal trade-off |
| --- | --- | --- | --- |
| **MPA** | Multi-page application navigates through distinct documents, commonly generated by the server. | Content, forms, administrative web UIs. | Full page navigation without partial update techniques. |
| **SPA** | One persistent client shell controls most navigation/views via client-side code. | Highly interactive client applications. | Bundle size, state, hydration, accessibility and SEO care. |
| **SSR** | Server renders requested HTML per request (possibly cached). | Personalized content and fast useful document responses. | Server workload and cache strategy. |
| **CSR** | Browser JavaScript performs most content rendering after initial document. | Interactive internal tools. | JS dependency and delayed useful content. |
| **SSG** | Pages are rendered to files at build time. | Marketing, documentation, blogs. | Rebuilds or dynamic integration for live data. |
| **ISR / incremental regeneration** | Pre-rendered pages refresh after deployment according to framework revalidation rules. | Mostly static catalogs with periodically updated data. | Cache staleness and platform-specific behavior. |
| **Hybrid rendering** | Static, server and client rendering are applied selectively by route/component. | Mixed content + authenticated features. | Complex cache, routing and hydration ownership. |
| Islands architecture | Primarily static/server HTML contains explicitly hydrated interactive islands. | Content-heavy sites needing selective interaction. | Island boundary and shared-state coordination. |
| Partial hydration | Only selected browser components receive client-side hydration. | Reducing JS cost of SSR pages. | Framework/toolchain coupling. |
| Progressive enhancement | Core content and forms work through standard HTML; JS layers add optional interactions. | Resilient public sites and administrative forms. | Interactive features need graceful fallback design. |
| Hypermedia / HTMX-style | Server returns HTML fragments and hypermedia links/forms drive partial updates. | SSR sites needing fast interactions without a full SPA. | Fragment contract, history and state coordination. |
| API-first | API contracts are explicit product interfaces and clients consume them. | Multiple clients or integrations. | Versioning, auth, observability and interface maintenance. |
| Headless | Content/business backend is separate from a presentation client consuming an API. | Multiple presentation channels or CMS reuse. | More distributed composition and preview/SEO complexity. |
| Jamstack-style | Prebuilt markup/assets are delivered by CDN with dynamic services via APIs or functions. | Static-first content with limited dynamic behaviors. | Service dependencies and rebuild/caching workflows. |
| **PWA** | Website gains installability and potentially offline/cached behavior via web platform APIs and service worker. | Field apps, offline forms and repeat-use workflows. | Storage lifecycle, updates, sync conflict and platform differences. |
| Microfrontends | Independently owned UI fragments or applications are composed into a user-facing experience. | Many autonomous frontend teams. | Runtime coupling, UX divergence and performance overhead. |
| Responsive/adaptive UI | Layout responds to viewport/capabilities or serves different UI variants. | Multi-device access. | Testing matrix; not a deployment architecture. |
| Static HTML site | Pages/assets require no application server for basic serving. | Brochure and simple information sites. | Dynamic state requires external services or separate backend. |

## Examples

~~~text
# SSR / progressive-enhanced PHP
app/{Controllers,Views}/
routes/
resources/css/input.css
public/assets/css/styles.css

# Static-first
src/pages/
src/components/
public/assets/
dist/              # actual generated output only

# Client-heavy SPA
src/features/
src/routes/
src/components/
public/
~~~

**Compatibility examples:** A Laravel site can be SSR + MPA + HTMX + Alpine + PWA. A static site can use islands and form APIs. A SPA can use SSR for initial content. PWA is not an alternative to MVC or modular monolith.

Standards and implementation obligations for accessible HTML, forms, URLs, caching and progressive enhancement belong to [WDBASIC](../../../Wdbasic/README.md).
