# WDBASIC Form Contract

> **Authority:** Binding form architecture and lifecycle contract  
> **Core entry point:** [`../README.md`](../README.md)  
> **Validation contract:** [`validation.md`](validation.md)  
> **Security contract:** [`security.md`](security.md)  
> **Architecture dependency:** [`../architecture_rules.md`](../architecture_rules.md)  
> **Accessibility dependency:** [`../tokens/accessibility.md`](../tokens/accessibility.md)

This contract governs forms rendered, processed, generated, embedded, or submitted by WDBASIC implementations.

## 1. Scope

This contract applies to:

- Public contact, estimate, quote, search, newsletter, registration, and application forms.
- Authentication, recovery, verification, and invitation forms.
- Client, employee, administrative, and authoring interfaces.
- Settings, filters, bulk actions, uploads, payments, and consequential actions.
- Multi-step and save-and-resume processes.
- HTMX-enhanced forms and server-rendered validation fragments.
- Forms generated by a CMS, builder, template, plugin, or AI-assisted authoring tool.
- Form-associated custom elements.
- Native or hybrid shells that submit equivalent data to a server.

A search field or single-action confirmation is still a form workflow when it collects or submits user input.

## 2. Core principles

Every form must:

- Use native HTML controls where they provide the required behavior.
- Use normal server submission as the baseline unless a documented product constraint makes that impossible.
- Keep the server authoritative for validation, authorization, business rules, and persistence.
- Collect only information required for the declared task.
- State purpose, requirements, formats, and consequences before they are needed.
- Preserve non-sensitive input after recoverable failure.
- Distinguish validation errors, authorization failures, conflicts, rate limits, and unexpected failures.
- Provide accessible error, success, pending, and recovery states.
- Remain secure when client validation, JavaScript, or HTMX is bypassed.
- Avoid treating validation as output encoding, sanitization, authorization, or injection prevention.

## 3. Standard form lifecycle

A form workflow follows this sequence:

1. **Render** — The server returns the form, purpose, labels, instructions, constraints, CSRF state, and current authorized values.
2. **Input** — The browser and assistive technologies expose native control semantics and relevant input assistance.
3. **Client constraint validation** — Native constraints and optional local enhancement identify obvious correctable errors.
4. **Submission admission** — The server verifies route, method, content type, request size, origin, CSRF, authentication, and request shape.
5. **Decoding and canonicalization** — The server decodes once and applies field-specific normalization without destroying meaningful user data.
6. **Syntactic validation** — Each value is checked for requiredness, type, length, shape, range, and allowed structure.
7. **Semantic validation** — Values are checked for domain meaning, cross-field consistency, current state, uniqueness where required, and business rules.
8. **Authorization** — The server verifies the actor may perform the action on the resolved object, tenant, account, or record.
9. **Abuse controls** — Rate limits, risk checks, honeypots, replay protection, upload controls, and accessible escalation are applied proportionately.
10. **Atomic effect** — Persistence and side effects occur transactionally or with documented compensation and idempotency behavior.
11. **Response** — The server returns a full response or fragment representing validation, conflict, rate limit, success, or failure accurately.
12. **Audit and notification** — Sensitive or consequential outcomes are recorded without logging secrets or unnecessary form values.

A client-side pass never skips server-side lifecycle stages.

## 4. Form definition record

Every reusable or consequential form should define:

```yaml
form:
  name: estimate-request
  purpose: collect information required to review a service request
  owner: leads
  route: /estimate
  methods: [GET, POST]
  rendering: server-html
  enhancement: htmx
  authentication: public
  authorization: create-lead
  csrf: required
  fields:
    - name: email
      type: email
      required: true
      autocomplete: email
      normalization: trim-surrounding-ascii-whitespace
      validation: email-address
      sensitive: personal
      retention: lead-policy
  unexpected_fields: reject
  maximum_request_size: <value>
  rate_limit: <policy>
  idempotency: duplicate-window
  success: redirect-303
  validation_response: 422
  conflict_response: 409
  audit_events: [submission-accepted, submission-rejected]
  evidence: <path>
```

## 5. Field contract

Each field defines:

- Stable field name and business meaning.
- Native control and submitted representation.
- Required or optional status.
- Permitted scalar, list, file, or structured shape.
- Minimum and maximum length, count, size, and range where applicable.
- Input-purpose and autocomplete behavior.
- Normalization policy.
- Syntactic rules.
- Semantic and cross-field rules.
- User-visible instructions and examples.
- Error codes and user-safe messages.
- Sensitivity classification.
- Retention and logging policy.
- Whether the value may be redisplayed after failure.
- Authorization or ownership implications.

Hidden fields, query parameters, cookies, headers, disabled controls, and JavaScript state are untrusted inputs when they influence a form action.

Visual state, native validity, ARIA state, server response, and stored state must not contradict one another.

## 7. Baseline HTML contract

- Forms use an explicit `action` and appropriate `method`.
- State-changing actions do not use `GET`.
- Controls have stable `name` values and persistent labels.
- Related controls use `fieldset` and `legend` where applicable.
- Submit buttons use specific action text.
- Native `required`, type, length, range, and step constraints are used when they accurately describe the field.
- Placeholder text is not the sole label or instruction.
- Autocomplete tokens are used deliberately.
- The form remains understandable when styles or enhancement scripts fail.
- `novalidate` is used only when the implementation supplies an equivalent accessible validation experience and server validation remains authoritative.

## 8. Response contract

Typical outcomes:

| Outcome | Typical response | Required behavior |
|---|---:|---|
| Successful full submission | `303` redirect | Prevent resubmission and provide a stable result URL. |
| Successful fragment submission | `200` or `204` | Return an accurate success state and announcement contract. |
| Malformed request | `400` | Do not treat malformed transport or syntax as ordinary field validation. |
| Authentication required | `401` or authentication redirect | Preserve safe recoverable context when appropriate. |
| Forbidden action | `403` | Do not reveal protected object details unnecessarily. |
| State conflict | `409` | Explain refresh, merge, retry, or replacement behavior. |
| Request too large | `413` | Explain limits before retry where safe. |
| Unsupported content type | `415` | Identify accepted submission encoding where appropriate. |
| Semantic validation failure | `422` when used by the application | Return field and summary errors with preserved safe values. |
| Rate limited | `429` | Provide retry guidance without exposing defensive thresholds unnecessarily. |
| Unexpected failure | `500` | Provide a user-safe recovery path and correlation identifier where useful. |

A project may use another documented convention, but status codes and visible outcomes must remain truthful and consistent.

## 9. HTMX and asynchronous validation

HTMX may improve continuity but must not create a second validation or security model.

Each enhanced form defines:

- Trigger and submitter.
- Request method and endpoint.
- CSRF transmission.
- Target and swap strategy.
- Pending and duplicate-submission behavior.
- Error-summary placement.
- Field-error replacement behavior.
- Focus destination.
- Status announcement.
- History behavior.
- Full-response fallback.

Asynchronous checks such as username availability, address lookup, or coupon verification are advisory until the final server submission revalidates the condition atomically.

## 10. Multi-step forms

A multi-step process must:

- Expose progress and the current step.
- Preserve already accepted information.
- Avoid asking for the same information again unless an exception applies.
- Revalidate dependent values when relevant state changes.
- Protect drafts according to their sensitivity.
- Define expiration and recovery behavior.
- Allow users to review and correct consequential information before final submission.
- Treat the entire process as one complete accessibility and security workflow.

## 11. Generated forms

Authoring tools that generate forms must:

- Produce labels, names, groups, constraints, and error relationships by default.
- Require an explicit server destination and processing owner.
- Prevent untrusted authors from choosing privileged fields, routes, recipients, or storage paths.
- Generate explicit allowlists rather than unrestricted object binding.
- Preserve CSRF, authorization, rate-limit, privacy, and retention policies.
- Warn when a requested field is sensitive, excessive, ambiguous, or unsupported.
- Validate generated output under [`../authoring/accessible-output.md`](../authoring/accessible-output.md).

## 12. Testing

Test every form for:

- Direct load and normal server submission.
- No JavaScript.
- Native client validation.
- Bypassed client validation.
- HTMX success and failure.
- Empty, boundary, malformed, unexpected, and duplicate input.
- Keyboard, screen reader, speech input, zoom, and narrow width.
- Slow network, retry, refresh, and duplicate submission.
- Authentication expiration and CSRF failure.
- Rate limiting and challenge fallback.
- Concurrent modification and stale data.
- Upload rejection and processing failure where applicable.
- Sensitive-data redaction in responses, analytics, and logs.

Reusable procedures follow [`../compliance/act-rule-template.md`](../compliance/act-rule-template.md) where applicable.
