# WDBASIC Form Security Contract

> **Authority:** Binding security contract for form rendering, submission, processing, and persistence  
> **Form entry point:** [`README.md`](README.md)  
> **Validation dependency:** [`validation.md`](validation.md)  
> **Security dependency:** [`../security-and-privacy.md`](../security-and-privacy.md)  
> **Architecture dependency:** [`../architecture_rules.md`](../architecture_rules.md)

This contract defines the minimum security controls for every WDBASIC form workflow.

## 1. Trust model

Treat all request-controlled data as untrusted, including:

- Visible controls.
- Hidden controls.
- Disabled or omitted controls.
- Query parameters.
- Route parameters.
- Cookies.
- Headers.
- Uploaded filenames and metadata.
- JavaScript and HTMX state.
- Custom-element form values.
- API and webhook data derived from form submissions.
- Values supplied by trusted partners or internal systems.

A field being generated by the server, hidden from the user, signed by JavaScript, or presented as read-only does not make it authoritative.

## 2. Request admission

Before field validation or business processing, verify:

- Route and allowed HTTP method.
- Accepted content type and character encoding.
- Maximum request and body size.
- Maximum field count, list count, nesting depth, and file count.
- Authentication state when required.
- Session validity.
- CSRF protection for cookie-authenticated state changes.
- Origin and request-context policy where applicable.
- Rate-limit and abuse-control state.
- Required idempotency or replay token.

Reject unsupported methods and content types before attempting ordinary field validation.

State-changing behavior must not be reachable through `GET`, `HEAD`, `OPTIONS`, or another method defined as safe.

## 3. CSRF protection

Cookie-authenticated state-changing forms require an explicit CSRF defense appropriate to the framework and deployment.

Use one of:

- Synchronizer token pattern.
- Signed double-submit cookie pattern.
- A framework-provided equivalent with documented guarantees.

Defense-in-depth controls should include, where supported:

- `SameSite` session-cookie policy.
- `Origin` verification.
- `Referer` verification when `Origin` is absent.
- Fetch Metadata request-header policy.
- Host and target-origin validation behind trusted proxies.

Rules:

- CSRF tokens are bound to the correct session or security context.
- Tokens use cryptographically secure generation or signing.
- Tokens do not appear in URLs, referrers, analytics, or ordinary logs.
- Token comparison is timing-safe where relevant.
- Token failure does not expose the expected token or internal session state.
- HTMX and asynchronous requests transmit the same protected context as full form submissions.
- `SameSite` is defense in depth and does not replace a proper CSRF control unless the narrowly documented deployment conditions justify that choice.
- Login, logout, invitation acceptance, email change, password change, payment, and other security-sensitive flows receive explicit CSRF review.

## 4. Authentication and session state

Forms requiring identity must verify the current session at submission time, not only when the form was rendered.

- Reauthenticate before sufficiently sensitive actions when policy requires it.
- Rotate session identifiers after authentication or privilege changes.
- Do not accept actor, role, tenant, permission, or authentication state from submitted form values.
- Preserve safe non-sensitive work when a session expires, where practical.
- Authentication and recovery errors must avoid account enumeration through message, status, redirect, or material timing differences.
- Password managers, paste, and standard autocomplete behavior remain supported.
- One-time codes and recovery tokens are single-use, bounded in lifetime, rate limited, and stored in a non-recoverable form where appropriate.

## 5. Authorization and object ownership

Every state-changing request verifies both:

1. The actor may perform the action.
2. The actor may perform it on the resolved object, tenant, account, record, or resource.

Rules:

- Resolve protected objects server-side.
- Do not trust hidden IDs, owner IDs, tenant IDs, prices, discounts, statuses, destinations, or permission flags.
- Prevent insecure direct-object reference by applying object-level authorization after resolution.
- Recheck authorization immediately before persistence when relevant state can change.
- Bulk actions authorize every affected object or reject the request according to an explicit atomicity policy.
- Disabled interface controls do not replace authorization.

## 6. Mass assignment and overposting

Automatic binding of arbitrary request fields to a domain model is prohibited.

Use:

- Explicit request or command objects.
- Per-form field allowlists.
- Explicit mapping from accepted input to writable properties.
- Separate user-editable and privileged properties.

Never mass-assign fields such as:

- Role or permission.
- Tenant or owner.
- Approval or verification status.
- Price, discount, tax, or balance.
- Internal workflow state.
- Audit fields.
- File storage path.
- Password hash or token state.
- Administrative flags.

Unexpected fields follow the policy defined in [`validation.md`](validation.md) and must not silently modify protected state.

## 7. Injection prevention

Input validation is not the primary defense against injection.

Use safe APIs that preserve the distinction between code and data:

- Parameterized database queries or safe ORM binding.
- Structured command APIs rather than shell construction.
- Safe mail, LDAP, XPath, template, and header APIs.
- Server-controlled mappings for dynamic identifiers such as sort fields or column names.

Rules:

- Do not concatenate submitted input into SQL, shell commands, templates, headers, filesystem paths, or interpreter expressions.
- Escaping is context specific and must not be treated as a universal defense.
- Validate dynamic identifiers against a server-defined allowlist.
- Apply least privilege to database, filesystem, queue, mail, and integration credentials.
- Never execute uploaded or submitted content as code because it passed field validation.

## 8. Output encoding and rich content

Every submitted value rendered later is encoded for its output context.

Contexts include:

- HTML text.
- HTML attribute.
- URL.
- JavaScript.
- CSS.
- JSON.
- Email headers and bodies.
- CSV or spreadsheet export.
- Logs and administrative viewers.

Rules:

- Prefer template systems with automatic context-sensitive escaping.
- Do not mark input as safe merely because it was previously validated.
- Rich HTML is sanitized using a reviewed parser-based sanitizer and explicit allowlist.
- Sanitization policy deliberately handles links, media, ARIA, IDs, language, direction, tables, and form elements.
- Content Security Policy is defense in depth and does not replace encoding or sanitization.
- Administrative interfaces must encode hostile submissions safely rather than trusting staff-only pages.

## 9. Redirects, URLs, and external destinations

When a form accepts or derives a redirect or callback destination:

- Prefer server-controlled route identifiers.
- Allowlist permitted origins and schemes.
- Reject protocol-relative, credential-bearing, malformed, and disallowed-scheme URLs.
- Normalize and compare using a trusted URL parser.
- Do not redirect to an arbitrary submitted URL after authentication or payment.
- Prevent server-side request forgery when the server retrieves a submitted URL.

## 10. Sensitive fields and privacy

Sensitive values require an explicit collection, transmission, retention, display, and deletion policy.

- Use secure transport.
- Never place sensitive values in URLs.
- Do not log passwords, one-time codes, CSRF tokens, access tokens, payment data, secret answers, or unnecessary personal content.
- Prevent sensitive values from entering analytics, session replay, error reporting, or client-visible diagnostics.
- Mask values only when masking still supports the task; do not imply masked data is absent from storage.
- Do not redisplay sensitive fields after validation failure.
- Use appropriate autocomplete values; do not disable password managers without a documented tested requirement.
- Minimize collected fields and retention.
- Protect draft forms and staged uploads according to their data classification.
- Clear sensitive temporary storage after completion, expiration, cancellation, or failure according to policy.

## 11. Duplicate submission, replay, and idempotency

Material actions must define duplicate and replay behavior.

Use idempotency keys, unique operation identifiers, database constraints, state-transition checks, or equivalent controls when duplicate submission could create:

- Multiple charges.
- Duplicate orders or leads.
- Repeated invitations or notifications.
- Duplicate file processing.
- Repeated destructive actions.
- Conflicting state transitions.

Rules:

- Disabling the submit button is only a user-interface aid.
- Idempotency state is scoped to the actor, operation, and relevant resource.
- Keys have bounded lifetime and cannot authorize a different operation.
- Retries return the existing outcome when safe rather than repeating the side effect.
- Expired or reused keys produce a documented conflict or recovery response.

## 12. Rate limiting and abuse prevention

Apply proportionate controls to public, authentication, recovery, invitation, upload, search, messaging, and expensive-processing forms.

Controls may include:

- Per-account, session, IP, device, route, tenant, or resource limits.
- Honeypot fields.
- Minimum-completion-time checks.
- Reputation and anomaly signals.
- Queueing and backpressure.
- Risk-based escalation.
- Temporary cooldowns.
- Accessible human-verification fallback.

Rules:

- Do not disclose exact defensive thresholds unnecessarily.
- Do not permanently punish shared networks or privacy tools without recovery.
- Preserve legitimate user data through recoverable challenge or rate-limit states where safe.
- Rate-limit responses are accessible and provide appropriate retry guidance.
- Security controls must not use disability, assistive technology, unusual input cadence, or privacy settings as proof of abuse.

## 13. Authentication-form protections

Authentication, registration, and recovery forms additionally require:

- Generic user-safe failure messages where enumeration is a risk.
- Comparable response behavior for existent and nonexistent accounts.
- Password-policy handling consistent with the current authentication baseline.
- Support for long passwords and printable characters.
- No silent password truncation.
- Throttling and credential-stuffing defenses.
- Secure account-recovery tokens and delivery channels.
- Verification of security-sensitive changes through an appropriate trusted channel.
- Notification of material account changes where policy requires it.

## 14. File upload security

Uploads use defense in depth.

Required controls:

- Authorize who may upload and to which object or tenant.
- Allowlist business-required extensions.
- Detect actual type; do not trust the submitted `Content-Type` header.
- Enforce file count, individual size, aggregate size, dimensions, duration, and archive-expansion limits as applicable.
- Generate storage filenames and object keys server-side.
- Treat the original filename as untrusted display metadata.
- Store outside executable paths and preferably outside the public web root.
- Serve through an authorization-aware handler when files are not intentionally public.
- Scan or sandbox files where appropriate.
- Apply content disarm and reconstruction for supported high-risk document types where required.
- Re-encode images when appropriate and validate decoded image content.
- Reject path traversal, alternate data streams, double extensions, dangerous archives, and parser bombs.
- Strip or preserve metadata deliberately.
- Quarantine until processing completes.
- Protect upload submissions against CSRF and replay.
- Define deletion, retention, and failed-processing cleanup.
- Keep parsing and transformation libraries patched and isolated with least privilege.

An `accept` attribute or filename extension check is not sufficient file validation.

## 15. Hidden, signed, and calculated values

When the browser must return a server-derived value:

- Prefer returning a stable opaque identifier and resolve current values server-side.
- Recalculate prices, totals, permissions, availability, and workflow state on the server.
- Use authenticated encryption or signing only when client round-tripping is necessary.
- Bind protected values to the intended user, purpose, and expiration.
- Reject expired, replayed, altered, or context-mismatched values.

A valid signature proves integrity of the signed data, not current authorization or business validity.

## 16. Transaction and concurrency security

- Apply state changes atomically where practical.
- Use optimistic or pessimistic concurrency deliberately.
- Prevent stale forms from overwriting newer protected data silently.
- Revalidate authorization, state, inventory, pricing, quotas, and uniqueness at commit time.
- Define compensation when external side effects occur outside the database transaction.
- Do not report success before required durable effects are confirmed, unless the interface explicitly communicates queued processing.

## 17. Error handling

Security failures return user-safe responses.

Do not expose:

- Stack traces.
- SQL or query fragments.
- Filesystem paths.
- Secret or token values.
- Expected CSRF values.
- Internal service names.
- Authorization rules.
- Upload scanner details that enable bypass.

Use correlation identifiers when useful. Keep detailed diagnostic context in protected logs rather than user-visible responses.

A security rejection must remain distinguishable internally from an ordinary validation error even when the public message is intentionally generic.

## 18. Logging and audit

Record security-relevant outcomes such as:

- Authentication and recovery failures.
- Authorization denials.
- CSRF failures.
- Rate-limit and abuse-control decisions.
- Unexpected or protected fields.
- Upload acceptance, rejection, quarantine, and scanning results.
- Consequential submissions and administrative changes.
- Idempotency conflicts and suspicious replay.
- Repeated state-transition failures.

Logs must:

- Use structured event types.
- Include time, outcome, route or operation, actor or pseudonymous identifier, object identifier where safe, and correlation identifier.
- Sanitize values against log injection.
- Exclude secrets and unnecessary form content.
- Be access controlled, retained deliberately, and protected against tampering.
- Distinguish user mistakes, accessibility barriers, provider failures, and malicious behavior when evidence supports the distinction.

## 19. Security testing matrix

Test each form for:

- Client-validation bypass.
- Missing and invalid CSRF tokens.
- Cross-origin and same-site request conditions.
- Unsupported methods and content types.
- Oversized body, excessive fields, nesting, and file counts.
- Unexpected and protected properties.
- Tampered IDs, tenant values, prices, roles, and workflow states.
- Object-level authorization failures.
- Duplicate and replayed submission.
- Concurrent update and stale-form behavior.
- SQL, template, header, path, command, and log injection payloads appropriate to the implementation.
- Stored and reflected XSS in every output context.
- Open redirect and server-side URL retrieval.
- Account enumeration and timing discrepancies.
- Rate-limit, lockout, challenge, and recovery behavior.
- File type spoofing, double extensions, archive bombs, metadata leakage, and malicious parser input.
- Sensitive-value exposure in URLs, responses, source maps, analytics, logs, and error tools.
- HTMX and full-page security equivalence.
- Authorization after session, role, tenant, or object state changes.
