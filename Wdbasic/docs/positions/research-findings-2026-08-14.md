# WDBASIC Research Findings Snapshot — 2026-08-14

> **Status:** Historical research snapshot  
> **Purpose:** Preserve the full set of WDBASIC/PAS findings developed in the August 14, 2026 research conversation  
> **Authority:** Informative historical record; does not override binding WDBASIC contracts  
> **Related positions:** [`pas-content-architecture.md`](pas-content-architecture.md), [`wdbasic-evaluation-model.md`](wdbasic-evaluation-model.md)

This file preserves the findings as a research record so later refinement does not erase how the current WDBASIC PAS and evaluation positions were derived.

## 1. Correction of the initial framing error

The first exploratory research pass incorrectly treated “WDBASIC” as if it might have an external or pre-existing meaning.

That framing was corrected.

For this project, **WDBASIC is the user's own name for a web-design-basics philosophy and experience framework**. It has no intended external meaning and should not be conflated with BASIC-family programming languages, unrelated acronyms, or third-party frameworks.

All later findings were recalculated from that premise.

## 2. Recalculated working definition

The recalculated analysis described WDBASIC as:

> A declarative, evidence-led web-design philosophy in which architecture, content, SEO, accessibility, trust, and conversion are designed as one system around the user's problem and intended outcome.

This is a descriptive synthesis, not a replacement for the binding framework contract.

## 3. Existing WDBASIC strengths identified

The analysis recognized that WDBASIC already established major foundations across three layers:

### Technical

- server-rendered primary HTML;
- HTMX-first server-owned interaction;
- minimal JavaScript;
- progressive enhancement;
- reusable server-side fragments/components.

### Structural

- modular components;
- semantic HTML;
- explicit architecture/governance;
- reusable layouts and interaction contracts.

### Conversion/content

- hero/value proposition;
- trust/proof;
- services/solutions;
- PAS-oriented benefit framing;
- FAQ/objection handling;
- final CTA.

The research therefore did not conclude that WDBASIC needed a completely new philosophy. It concluded that the existing philosophy could be made more explicit and measurable around **semantic progression and user decision-making**.

## 4. PAS evolved from copy block to page architecture

The central finding was that Problem–Agitate–Solution should not be treated only as a short copywriting formula.

WDBASIC can distribute PAS across the whole page:

```text
Intent
→ Problem
→ Consequence
→ Solution
→ Validation
→ Objection
→ Action
```

This is a semantic sequence, not a mandatory visual template.

## 5. Expanded PAS model

The analysis effectively expanded PAS into:

```text
P → A → S → V → C
```

Where:

- `P` = Problem recognition
- `A` = Agitation / relevant consequence
- `S` = Solution
- `V` = Validation / proof
- `C` = Conversion / action

This expansion reflected the practical questions a visitor asks:

1. Do you understand my problem?
2. Does it matter?
3. Can you solve it?
4. Why should I believe you?
5. What do I do next?

FAQ and objection handling sit between validation and action where needed.

## 6. Ethical definition of agitation

The analysis rejected fearmongering as a default interpretation of “Agitate.”

The retained WDBASIC definition is:

> Explain the relevant consequences, inconvenience, risk, cost, delay, or missed outcome associated with leaving the identified problem unresolved. Claims must remain proportional, supportable, and directly connected to the problem.

This was intended to prohibit:

- fabricated urgency;
- catastrophizing;
- unsupported danger claims;
- endless restatement of pain;
- manipulative fear escalation;
- AI-generated semantic repetition.

## 7. Direct PAS formula finding

The initial exploratory response included a **direct PAS formula**.

The exact coefficient set from that first response was not recoverable with enough confidence during the later consolidation.

The preserved generic structure is:

```text
PAS = (wP × P) + (wA × A) + (wS × S)
```

with:

```text
wP + wA + wS = 1
```

The historical coefficients remain unresolved and must not be guessed.

## 8. Later experimental PAS subscore

A later recalculation proposed:

```text
PSA = P(7) + A(5) + S(8)
```

This is **not** the unrecovered first formula.

The rationale was:

- Problem = 7 because recognition/relevance is foundational;
- Agitate = 5 because consequence is useful but should not dominate;
- Solution = 8 because WDBASIC should prioritize helping over frightening.

## 9. Threat/efficacy diagnostic

A separate research analogy was drawn from the Extended Parallel Process Model.

This was **not** the PAS score itself.

The useful distinction was:

```text
Threat = severity + susceptibility/relevance
Efficacy = response efficacy + self-efficacy/actionability
```

The review question became:

> Does the page make the problem feel more overwhelming than the proposed action feels credible and achievable?

This is retained only as a secondary diagnostic for aggressive consequence/fear messaging.

## 10. Broader WDBASIC audit model

The analysis proposed:

```text
WDBASIC = D + P + X + T + A + C
```

with the working 100-point distribution:

| Dimension | Weight |
|---|---:|
| Discoverability / SEO | 20 |
| Problem–solution alignment | 20 |
| Experience / usability | 15 |
| Trust / validation | 15 |
| Accessibility | 15 |
| Conversion clarity | 15 |
| **Total** | **100** |

The purpose was diagnostic, not to manufacture an industry score.

## 11. Discoverability findings

The SEO/discoverability dimension included:

- server-rendered primary content;
- crawlable links;
- indexability/canonical integrity;
- semantic structure;
- useful title/H1 alignment;
- search-intent coverage;
- unique content;
- local relevance where genuine;
- descriptive image context;
- internal linking;
- correct HTTP/error behavior;
- avoidance of doorway/location duplication;
- avoidance of keyword stuffing and phrase-density thinking.

The preferred conceptual model became:

```text
Search Intent
→ Problem
→ Consequence
→ Solution
→ Evidence
→ Conversion
```

rather than:

```text
Keyword
→ Repeat Keyword
→ Rephrase Keyword
→ CTA
```

## 12. Experience/usability findings

The proposed experience review included:

- hierarchy;
- predictable navigation;
- responsiveness;
- typography/readability;
- content grouping;
- low-friction forms;
- understandable feedback/errors;
- progressive enhancement;
- no unnecessary client-only state dependency;
- practical performance;
- recovery behavior;
- appropriate input-method support.

## 13. Trust/validation findings

Trust was treated as its own decision stage rather than a decorative testimonial strip.

Potential validation included:

- authentic reviews;
- case studies;
- real project photos;
- business identity;
- location/service-area truthfulness;
- transparent process;
- evidence-backed qualifications;
- realistic claims;
- appropriate pricing/process information;
- accountable authorship/business identity;
- proof proportional to the materiality of the claim.

## 14. Accessibility findings

Accessibility was retained as a full-system constraint, including:

- semantic headings;
- native controls;
- visible focus;
- labels/instructions;
- programmatically connected errors;
- meaningful alternative text;
- no color-only meaning;
- logical source order;
- zoom/text resizing;
- reduced motion where applicable;
- keyboard operation;
- responsive accessibility;
- accessible validation/recovery;
- media alternatives;
- user agency.

The analysis explicitly separated any heuristic accessibility score from formal WCAG conformance.

## 15. Conversion findings

Conversion clarity included:

- a clear primary action;
- above-fold CTA where appropriate;
- repeated CTAs at natural decision points;
- action-oriented wording;
- reasonable form friction;
- objection handling;
- response expectations;
- alternative contact paths where useful;
- CTA intensity matched to user readiness;
- no fake urgency or deceptive defaults.

Retained rule:

> CTA intensity should match user intent.

## 16. Component semantic-role mapping

The analysis mapped components to the job they perform:

| Component | Semantic role |
|---|---|
| Hero | Problem + Solution + Action |
| Proof strip | Validation |
| Problem section | Problem |
| Consequence section | Agitate / Consequence |
| Services | Solution |
| Process | Solution + uncertainty reduction |
| Case study | Solution + Validation |
| Reviews | Validation |
| FAQ | Validation + objection resolution |
| Estimate/contact form | Action |
| Final CTA | Action |

The finding was that component **names are not enough**. Reviewers should ask what semantic job the component actually performs.

## 17. Page-deficit diagnostic

Example page:

```text
Hero
→ Services
→ Services
→ Services
→ CTA
```

Possible diagnosis:

```text
Problem: weak
Consequence: absent
Solution: excessive/repetitive
Validation: absent
Objection resolution: absent
Action: present
```

This explained why some pages feel thin or unfocused even when they contain many words.

## 18. Semantic anti-repetition rule

A key governance finding was:

> A later component should not merely paraphrase the semantic job already completed by an earlier component unless it introduces new evidence, specificity, context, or decision value.

Additional acceptable reasons to revisit a semantic job include:

- a new user question;
- a concrete example;
- a different buyer stage;
- a new proof point;
- a different constraint or decision criterion.

This rule was specifically intended to fight AI-generated “more content” that is only reworded duplication.

## 19. Seven proposed WDBASIC laws

The analysis proposed:

1. User intent precedes interface.
2. Problem precedes solution.
3. Consequence must be proportional.
4. Solutions require evidence.
5. Every section must advance understanding.
6. Conversion must follow readiness.
7. The page must remain fundamentally usable without client-side application logic.

These were preserved as practitioner-law candidates, not silently promoted into binding contracts.

## 20. Consolidated page sequence

The final synthesis was:

```text
Intent
→ Problem
→ Consequence
→ Solution
→ Validation
→ Objection
→ Action
```

with the following constraints applying across the entire sequence:

- SEO/search architecture;
- accessibility;
- performance;
- semantic HTML;
- modularity;
- progressive enhancement;
- truthful claims;
- evidence;
- security/privacy where applicable.

The important conceptual change was to treat those disciplines as constraints around the entire user journey rather than bolt-on checklists.

## 22. Evidence-boundary finding

The consolidation established a classification discipline:

- external requirement;
- external guidance/research-supported principle;
- binding WDBASIC contract;
- WDBASIC practitioner position;
- WDBASIC heuristic;
- unresolved historical finding.

This classification is essential because WDBASIC intentionally combines standards, research, practitioner experience, design philosophy, and diagnostic heuristics without pretending they all have the same evidentiary status.
