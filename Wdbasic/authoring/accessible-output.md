# WDBASIC Accessible Output Contract

> **Authority:** Binding generated-content and export contract  
> **ATAG dependency:** [`atag-2.0.md`](atag-2.0.md)  
> **Component dependency:** [`../components/component-contracts.md`](../components/component-contracts.md)  
> **Non-web dependency:** [`../non-web-accessibility.md`](../non-web-accessibility.md)

This contract governs HTML, fragments, templates, emails, exports, native-shell content, and other output produced or transformed by an authoring tool.

## 1. Output principle

Generated output must be accessible by default and must not depend on post-publication repair for predictable failures.

The output contract applies to:

- Full HTML pages.
- HTMX fragments.
- Reusable sections and widgets.
- Custom-element markup and configuration.
- Form markup.
- Navigation.
- Structured data tables.
- Media embeds.
- Transactional and marketing emails generated by the product.
- Exported HTML.
- PDF, office-document, EPUB, and other non-web formats.
- Content embedded inside native or hybrid application shells.

Each output type must identify its applicable accessibility baseline. Web WCAG evidence cannot silently stand in for a native-shell or document-format evaluation.

## 2. Output inventory and ownership

Maintain an inventory containing:

- Output type.
- Generator, template, or transformation path.
- Owning package or domain.
- Applicable standards and versions.
- Source semantics available.
- Accessibility metadata supported.
- Sanitizer or transformation policy.
- Validation commands.
- Readers, clients, browsers, or platforms tested.
- Known limitations.
- Owner and review condition.

Uninventoried output must not be included in a broad accessibility claim.

## 3. Complete HTML document output

A complete page must provide:

- Correct document language and direction.
- Unique meaningful title.
- One discoverable main region.
- Logical headings.
- Bypass mechanism for repeated blocks.
- Crawlable navigation where public.
- Correct status and canonical URL behavior.
- Metadata managed by the product.
- Valid responsive and no-JavaScript behavior.
- Correct accessibility relationships after every render.

## 4. Fragment output

A generated fragment must include all state and semantics required to stand correctly inside its documented target.

It must preserve:

- Unique IDs.
- Labels and descriptions.
- Current, selected, expanded, invalid, busy, and disabled state.
- Language and direction.
- Focus and announcement expectations.
- Correct empty, validation, conflict, error, and success output.
- Direct-load or full-response fallback when required.

A fragment must not depend on an undocumented script to repair missing semantics after insertion.

## 5. Component and custom-element output

Generated components must:

- Use native HTML first.
- Provide complete states.
- Generate unique identifiers.
- Preserve valid relationships.
- Provide accessible names and descriptions.
- Maintain keyboard behavior.
- Return correct server and ARIA state.
- Remain usable without enhancement scripts where required.

When output includes custom elements or shadow DOM:

- The generated host, internals, slots, labels, descriptions, focus behavior, and form participation must follow [`../components/component-contracts.md`](../components/component-contracts.md).
- Accessibility must be verified in the computed accessibility tree, not inferred from source markup alone.
- A functional light-DOM or native fallback must exist when the selected platform or browser baseline cannot expose the custom control reliably.

Do not generate a visual component without the behavior required by its semantic role.

## 6. Images and graphics

The output system must support:

- Meaningful alternative text.
- Explicit decorative treatment.
- Captions and attribution.
- Stable dimensions.
- Responsive sources.
- Permission and source records.
- Text equivalents for charts, diagrams, and data graphics.

Do not automatically copy filenames, raw prompts, camera metadata, or generic object labels into alternative text as final values.

AI-generated alternative text remains a suggestion until reviewed against the image, purpose, and surrounding content.

## 7. Links and actions

- Links have meaningful destinations and names.
- Buttons perform actions.
- Empty controls are prohibited.
- Visible labels are included in accessible names.
- Repeated generic actions identify their target.
- New-window behavior is deliberate and communicated when material.
- Download links identify file type and size when that information materially affects the user.
- Generated actions do not rely on color, icon shape, hover, or pointer precision alone.

## 8. Forms and human verification

Generated forms must include:

- Persistent labels.
- Correct control type.
- Name and submitted value.
- Autocomplete when appropriate.
- Instructions and constraints.
- Required status.
- Error association.
- Error summary for complex forms.
- Server validation and preserved input.
- Success and recovery states.
- Review or reversibility for consequential submissions.

CAPTCHA, proof-of-humanity, anti-bot, or risk challenges must:

- Provide an accessible alternative that does not depend on one sensory or cognitive ability.
- Explain the task and recovery path.
- Preserve entered form data after challenge failure.
- Avoid blocking password managers, paste, assistive technology, or legitimate privacy tools without a documented and tested reason.
- Fail safely when the third-party provider is unavailable.

An authoring tool must not generate an inaccessible challenge as the only submission path.

## 9. Tables and structured data

Generated data tables must preserve:

- Caption or accessible purpose.
- Header cells.
- Scope or header relationships.
- Logical reading order.
- Sort state and named controls.
- Header/value relationships at narrow widths.
- Empty, loading, error, and pagination state.

A visual card transformation must not destroy tabular relationships.

Complex grids require documented keyboard, focus, selection, editing, and accessibility-tree behavior.

## 10. Media

Generated media output must carry the applicable caption, transcript, description, control, and autoplay requirements from [`../media-accessibility.md`](../media-accessibility.md).

The tool must not publish media while required accessibility metadata is silently discarded.

Third-party players remain within scope when relied upon. Provider limitations must be identified and may prevent a conformance claim.

## 11. Localization

Generated output must preserve:

- `lang` and `dir`.
- Passage-language metadata.
- Locale formatting.
- Bidirectional isolation.
- Translated labels, errors, captions, transcripts, alternative text, and metadata.
- Unicode content.
- Logical layout and reading order.

See [`../internationalization.md`](../internationalization.md).

## 12. Cognitive clarity

Generated pages, forms, workflows, emails, and documents follow [`../cognitive-accessibility.md`](../cognitive-accessibility.md).

Templates must not generate:

- Unexplained urgency or countdowns.
- Dense unstructured instructions.
- Ambiguous action labels.
- Important consequences hidden only in tooltips.
- Multi-step processes without progress and recovery context.
- Repeated requests for information already available in the process without a valid reason.

## 13. Sanitization and preservation

Sanitization must remove unsafe content without unnecessarily removing accessibility semantics.

The sanitizer policy must deliberately handle:

- `aria-*` attributes.
- `role`.
- `lang` and `dir`.
- IDs and references.
- Native table and form semantics.
- Custom elements and permitted attributes.
- Caption and media tracks.
- SVG titles, descriptions, and unsafe scripting.

Unsafe ARIA is not preserved merely because it is accessibility-related.

When sanitization removes or rewrites accessibility metadata, the tool must report that transformation or provide a review path.

## 14. Import and migration

When importing existing content:

- Preserve valid semantics.
- Identify unsupported constructs.
- Report accessibility metadata that cannot be mapped.
- Avoid converting semantic structures into presentational markup.
- Provide a review queue for uncertain repairs.
- Preserve source language and direction.
- Preserve caption, transcript, alternative-text, and table metadata.
- Record which original accessibility claims no longer apply after transformation.

Automatic repair must not invent author intent without review.

## 15. Email output

Generated email must account for the limitations of declared email clients.

At minimum:

- Use meaningful source order.
- Provide a useful subject and preheader.
- Use real text rather than image-only copy.
- Include meaningful link text.
- Provide alternative text and explicit image dimensions.
- Preserve readable contrast without relying on background images.
- Use table markup for layout only when necessary and prevent layout tables from being announced as data tables.
- Ensure actions remain understandable when images, CSS, or scripts are unavailable.
- Provide a browser or plain-text alternative when required by the product.

Do not claim web-page WCAG conformance for an email solely because its source template passed a browser-based checker.

## 16. EPUB output

EPUB output must follow the selected EPUB and EPUB Accessibility versions.

Record:

- EPUB version.
- EPUB Accessibility version.
- WCAG version and level used by the publication.
- Accessibility metadata.
- Navigation and reading order.
- Alternative content.
- Media overlays.
- Reading systems tested.
- Validation tools and versions.

The generator must preserve semantics and metadata required by the selected EPUB Accessibility baseline.

## 17. PDF and office-document output

PDF and office-document output must select an applicable format-specific accessibility baseline or procurement requirement.

The generator must preserve, where supported:

- Title and document language.
- Tagged reading order.
- Headings and lists.
- Table headers and relationships.
- Alternative text.
- Link purpose.
- Form labels and instructions.
- Bookmarks or navigation for long documents.
- Color and contrast.
- Metadata required by the selected format.

An image-only PDF or flattened visual export is prohibited when an accessible structured document is expected.

When a format cannot preserve required semantics, the tool must warn the author and provide another accessible format or equivalent.

## 18. Native and hybrid output

Content rendered inside Wails or another native shell follows [`../non-web-accessibility.md`](../non-web-accessibility.md).

Verify:

- Web content accessibility.
- Native chrome and controls.
- Focus transfer between native and web surfaces.
- Platform scaling and accessibility settings.
- Permission, install, offline, and update flows.
- Embedded web-view accessibility-tree behavior.

## 19. Output verification

Test generated output for:

- HTML and relationship integrity.
- WCAG coverage.
- Repeated component rendering.
- Custom-element and shadow-DOM behavior.
- No-JavaScript baseline where applicable.
- HTMX replacement.
- Localization and RTL.
- Cognitive clarity.
- Media equivalents.
- Security policy compatibility.
- CAPTCHA or human-verification alternatives.
- Email-client limitations.
- Native-shell behavior.
- Format-specific PDF, office, or EPUB accessibility.
- Reader, viewer, browser, or platform limitations.

Reusable checks follow [`../compliance/act-rule-template.md`](../compliance/act-rule-template.md).
